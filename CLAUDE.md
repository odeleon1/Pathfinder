# CLAUDE.md — Pathfinder

This file is read automatically by Claude Code at the start of each session. It carries how to work on this project and the hard environment rules. The full project plan (phases, architecture, risks) lives in **BRIEFING.md**, and the current-phase node graph + topic contract live in **ARCHITECTURE.md**, both at the repo root — read them before doing project work.

**Scope at a glance:** Pathfinder has a **back-end** (on-Jetson pipeline: mono camera → depth network → scale recovery via SPOT odometry → dense map) and a **front-end** (viewer that shows the 3D map being built, colored with the camera's RGB). See BRIEFING.md for detail.

## How to work with Orlando

**Communication**
- Direct and casual. No filler, no preamble, no "great question." Short asks get short answers.
- Human-sounding output. Don't pad.

**Calibrated honesty (default mode)**
- Agree when he's right, say so plainly, move on. Don't invent caveats to seem balanced.
- Push back directly when something's wrong or when there's a better approach — lead with the correction, then the reasoning, then the path forward.
- Don't manufacture disagreement to look rigorous. No yes-man behavior, no reverse-sycophancy.
- Calibrate the size of the reaction to the size of the issue.

**Learning is a primary goal of this project — equal to the code working**
- Explain the *why*, not just the *what*. When a step looks like a magic incantation, say what it's actually doing so it doesn't stay magic.
- When things get complex or non-obvious, explain the concept alongside the how-to.
- Don't lecture on routine stuff — that buries the parts that actually deserve attention. Calibrate depth to the stakes.
- If he says he wants to test himself, explain *less* on purpose — let him reason it through first, then confirm or correct.
- If an explanation lands at the wrong level (too basic / too deep), he'll say so; adjust from that rather than guessing.

## Hard rules (violating these causes real failures)

1. **Build TensorRT engines ON THE JETSON only.** Engines are specific to the exact GPU + TRT version. Never build on another machine and trust the result.
2. **Depth model: Small variant only.** Base/Large don't fit in 8GB on Orin. Don't suggest them.
3. **FP16 is mandatory.** INT8 is the fallback only if FP16 framerate is unacceptable.
4. **If/when containerizing, confirm GPU visibility inside the container first.** GPU passthrough into Docker is a classic Jetson failure point. (Development is native — this applies later.)
5. **Verify versions, don't assume.** Library/package/SDK versions on JetPack move and are interdependent. Check what's actually installed.
6. **cuVSLAM is off the table.** Stereo/multi-camera only. This is a mono camera. Don't propose it.

### Phase 1a — ✅ DONE (laptop WSL2 PoC)

**Result:** Full pipeline running on WSL2. TUM fr1/desk → depth_anything_node → rgbd_odometry → rtabmap → rtabmap_viz. Camera trajectory and growing dense point cloud confirmed. Pipeline logic proven.

**Durable gotchas:**
- Metric Depth Anything V2-Small runs at ~1.567 Hz on RTX 2000 Ada (avg 638ms/frame). Frame publisher must run at ≤1 fps — faster rates cause `approx_sync` timestamp misses and the map silently fails to build.
- `ament_python` hardwires `/usr/bin/python3` into entry point scripts regardless of venv. Fix: add venv site-packages to PYTHONPATH in `~/.bashrc`.
- HuggingFace pipeline `"depth"` key returns normalized uint8 (0–255), not metric depth. Use `result["predicted_depth"].squeeze().cpu().numpy()` for metres.
- `pathfinder_venv` must be created with `--system-site-packages` so rclpy and other ROS Python packages are visible inside it.
- `transformers` ≥ ~4.50 requires `torch.float8_e8m0fnu` (PyTorch 2.7+ only). Pin `transformers==4.46.3`.
